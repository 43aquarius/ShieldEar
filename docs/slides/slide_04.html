总体架构
ARCHITECTURE
一份引擎，跑在两端——谁也糊弄不了谁

浏览器先判一遍、服务端再核一遍，跑的是同一份 TypeScript 引擎：录音文件与实时通话的结论完全一致，客户端结果可被独立复核。检测不快不行、存证不严不行——这两个要求决定了下面五层；而每一层都有对应的服务端接口与数据落盘位置，不是纸面架构。

L1 采集 —— 麦克风实时流（AudioWorklet 16kHz）· 文件导入 · TTS现场合成，统一为单声道标准输入

L2 检测引擎

纯 TypeScript 零依赖，八维特征 + 2s 窗 / 1s 步进 / 50% 重叠滑窗

DSP 基座：FFT 512 点 · Hann 窗 · 自相关基音（抛物线精化）· 抗混叠重采样

「全片最厚的一层——左右两端跑同一份代码」

L3 判决融合 —— 中值滤波 + 指数平滑 + 能量加权整段判决，静音窗显式排除；检出阈值 0.72 · 可疑 0.50，四级风险分级 0.35 / 0.55 / 0.75

L4 业务 —— SHA-256 证据固定 · 案件编号 SS-日期-序号 · WAV 证据下载 · 八章可打印核验报告

L5 展示 —— 单页应用零跳转，答辩演示全程不切屏

同构引擎的价值：检测结论不因端而异——这是证据链成立的技术前提。
架构五层，从下往上过一遍：L1采集，把麦克风实时流、文件导入和现场合成统一成16kHz单声道标准输入；L2是全片最厚的检测引擎，纯TypeScript零依赖，八维特征加2秒窗、1秒步进的滑窗，DSP基座是FFT加Hann窗加自相关基音；L3用中值滤波、指数平滑、能量加权融合出整段判决，检出阈值0.72，四级风险分级的线在0.35、0.55、0.75；L4做SHA-256证据固定、SS-日期-序号案件编号、WAV证据下载和八章核验报告；L5单页展示零跳转。重点是同构引擎：浏览器和服务端跑同一份代码，检测结束还会自动POST服务端复核、两遍一致才入库——这是证据链成立的前提。为什么敢说能落地？纯CPU、一套语言栈、SQLite本地落盘可审计，四个接口都在。
